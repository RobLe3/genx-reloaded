# Quality and completion

Use for a substantive rewrite, rejected draft, or requested refinement. Apply only checks relevant to the requested output. These are editorial acceptance criteria, not a validated recruitment scale.

## Acceptance criteria

| Dimension | Satisfactory evidence | Repair trigger |
| --- | --- | --- |
| Tone and agency | Support matches the user's energy; urgent requests receive the work; disclosures remain optional | Repeated pep talks, forced positivity, a generational insult, or an unwanted disclosure |
| Factual fidelity | Every substantive change is supported by supplied or inspected evidence, with actual dates and scope | Upgraded title, qualification, language, metric, ownership, or project maturity |
| Target relevance | Opening identifies the intended role and supported relevant evidence; genuine gaps are visible in review notes | Generic summary, keyword stuffing, or unexplained relevance |
| Historical value | Older evidence is retained or compressed for a reason tied to the target | Automatic age cutoff or loss of uniquely relevant experience |
| Human readability | Opening answers the five first-page questions; bullets carry concrete meaning | Tiny text, dense repetition, jargon without context, or an ungrounded slogan |
| File integrity | Requested output exists, is visually inspected where possible, and has local extraction checked | Missing text, broken associations, clipped content, unresolved revisions, or unperformed checks described as passed |
| Useful finish | Candidate receives usable copy, material open issues, and a manageable next step | Advice without a draft, endless intake, an ATS guarantee, or a methodology report longer than the useful output |

For tightly bounded text requests, carry out factual and task checks silently unless a material issue or requested verification needs a note. Routine file-check disclaimers and readiness labels need not consume the candidate's word budget. When verification is requested, explain the checks actually performed and their limits. A pause-only handover should not add an unagreed future task.

Do not average these into a score. A factual failure cannot be offset by good layout.

## Bounded repair loop

1. Preserve the current usable version and the person's stated preferences.
2. State the observed problem using a source passage, file observation, or user feedback.
3. Distinguish a content defect from missing evidence, a tool limitation, or a style preference.
4. Make the smallest correction that addresses the problem without weakening factual boundaries.
5. Recheck the changed dimension and any connected claim or layout affected by the edit.
6. Deliver when the requested scope is satisfactory. If another pass would add little, stop. If a fact or capability blocks completion, deliver the useful partial result and name that specific limitation.

When user feedback changes a preference, apply it. When it asks for an unsupported claim, offer a strong truthful alternative. Do not repeat the entire workflow because one bullet needs revision.

## Safe learning from use

Keep the person's CV, private experience, rejection letters, and identifying details out of reusable instructions and public issues. With authorization to improve the skill, translate the failure into a fictional example and a general method. Add a focused regression case for a demonstrated failure; preserve failed results and describe the correction.

Do not claim that self-review creates independent evidence, that one successful scenario proves broad reliability, or that passing a helper script proves an employer will select the candidate.
